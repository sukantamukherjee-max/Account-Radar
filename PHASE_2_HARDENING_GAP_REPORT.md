## A. Already implemented

These parts of the approved Phase 2 hardening direction are solidly in place and should not be redone:

1. **Three-tier evidence ladder** (`DIRECT_EVIDENCE` / `STRONG_INFERENCE` / `WEAK_RELEVANCE`) — `commercial/models.py`. Fully deterministic, source-of-truth for everything downstream.
2. **Organization-association gate** (item 1, partially — see below) — `commercial/evidence_mapping.py::_is_organization_associated`. Sentence-local (radius-1) check that the *organization's own name* co-occurs with a matched capability term before it can promote to `direct_evidence`. Also applied (radius-0, same-sentence only) to generic-trigger `strong_inference` promotion.
3. **LinkedIn personal-profile hard cap**, enforced two ways (URL-derived, independent of upstream `source_type`; plus a final output clamp) — robust against the H3.1 regression class.
4. **Technographics / current-state source handling** — third-party technology-stack pages are capped at `weak_relevance` unconditionally (`_is_third_party_technographics`).
5. **Incumbent/vendor evidence separation** — `commercial/incumbents.py`, never promotable to a `CapabilityMapping` or opportunity by itself; attached only as `incumbent_context` notes.
6. **Deterministic opportunity/hypothesis engine** — `commercial/opportunities.py`, excludes `weak_relevance`, produces a bounded ranked shortlist with hypothesis/rationale/who/conversation/next_step language, all sourced from the catalogue, none invented.
7. **Deterministic Next-Best-Action safety net** — `ai/synthesis.py::_ground_and_build_result`. If the AI returns zero grounded actions, the deterministic opportunity shortlist fills the gap, explicitly tagged `origin=deterministic_guardrail`.
8. **AI grounding against invented facts (item 7)** — implemented thoroughly:
   - Unknown `capability_id` → narrative dropped, noted.
   - `cited_source_urls` checked against that capability's *own* `direct_evidence`/`strong_inference` sources only (`evidence_index`) — a `weak_relevance` source, a signal URL, an incumbent URL, or a deterministic-action-candidate URL can never become a `cited_source_url`, because the prompt never offers those as citable and the grounding check only accepts URLs present in `report.capability_mappings` for that specific capability at eligible evidence levels. This matches the "ONLY legal citation URLs are in that capability's capability_evidence" requirement exactly.
   - `next_best_actions` for a non-eligible capability → dropped, noted.
   - `evidence_level`/`confidence`/`best_evidence_level` are always copied from the real `CapabilityMapping`, never computed or invented by the model.
   - AI's proposed `rank` is a hint only; final order is a deterministic re-sort.
   - Structural tests confirm the report is never mutated by synthesis and grounding is pure given a fixed AI response.
9. **WATCH / UNDERSTAND / DECIDE / ACT tab structure** — `app.py`, all four present with roughly the content the Phase 2 README describes (signals/radar in WATCH, narrative/capability/incumbent/people context in UNDERSTAND, ranked hypotheses in DECIDE, AI actions + evidence explorer in ACT).
10. **Insufficient-evidence handling, end to end** — `research/analysis/qualification.py` → `AccountRadarReport.status` → surfaced as a UI warning banner and short-circuited before AI synthesis is even attempted.
11. **No hardcoded organization/sector/country names** — still enforced by AST-based tests across `research/`, `commercial/`, and `ai/`; catalogue remains generic JSON.

## B. Partially implemented

1. **Item 1 — Localize signal-to-trigger association.** Only *half* of this is done. `_is_organization_associated` (radius=0) is applied to the **generic trigger term itself** (does "new facility" sit in the same sentence as the org name?) — but the **qualifying `Signal` that grounds the promotion is never checked for locality against the trigger term at all.** `qualifying_signal = next((s for s in signals if s.signal_type in _QUALIFYING_SIGNAL_TYPES), None)` is picked from `extract_signals(source)` — the *first* qualifying signal found anywhere in the source, with no positional relationship to the matched `generic_hits` term. This is precisely the reported failure mode: *"a generic trigger... can be combined with a qualifying business signal found elsewhere in the same source."* The org-association half of the fix reduces false positives (the trigger word itself must be near the org name), but does not require the *signal* to be near the *trigger* — so a source that mentions the org + "acquisition" in one sentence and "partnership" in an unrelated sentence elsewhere will still fire.

2. **Opportunity-radar duplication (item 8, "avoid duplicating opportunity-ranking logic between WATCH and DECIDE").** The *computation* is not duplicated — `opportunities` is built once in `main()` (from `entry`/`report`) and passed by reference into both `_render_watch` and `_render_decide`. But the same ranked opportunity list is *displayed* in both tabs (a compact "Opportunity radar" progress-bar view in WATCH, the full ranked cards in DECIDE), which blurs the intended WATCH/DECIDE distinction (WATCH = "what changed", DECIDE = "where are the strongest validated hypotheses"). Not a correctness bug, but worth a product decision on whether WATCH should show opportunity *scores* at all, or just the underlying signals/events that feed them.

3. **Item 9 — "what we don't know" visibility.** Partially present: the top-level `insufficient_evidence` case is surfaced clearly as a warning banner. But once a corpus is `qualified`, the more granular uncertainty already computed by the pipeline is **not surfaced in the UI at all**: `qualification.corpus_reason` (e.g. "lacks LinkedIn evidence"), `qualification.disqualified_count`/`disqualified_reasons` (sources acquisition found but which were excluded from analysis), and the count/nature of `weak_relevance` evidence are all present in the report JSON but never rendered. A user watching a "qualified" account currently has no way to see *what evidence was thrown out and why*.

## C. Not implemented

1. **Item 2 — Narrow inference-qualifying signals for generic-trigger promotion.** `_QUALIFYING_SIGNAL_TYPES` (used by Rule 4, the generic-trigger → `strong_inference` path) still includes `partnership`, `investment`, and `contract_award` — exactly the three signal types the approved direction says "must not independently promote a generic technology trigger to STRONG_INFERENCE." Today they still can. (Note: `_TECH_EVENT_SIGNAL_TYPES`, the narrower set used for the *direct_evidence*-via-single-keyword path, already correctly excludes them — the narrowing was done for direct evidence in Phase 1C‑H2 but never carried over to the generic-trigger inference path, which is Rule 4's separate, still-broad `_QUALIFYING_SIGNAL_TYPES` gate.)

2. **Item 3 — `evidence_category` field.** Absent from `CapabilityMapping` (`commercial/models.py`), from `evidence_mapping.py`'s classification logic, and from every serialization path (`to_dict()`, `chain_view()`, the AI prompt block). Zero occurrences anywhere in the codebase.

3. **Item 4 — `inference_cluster_id`.** Same: does not exist anywhere. There is currently no way to tell, from the data, that (say) four `strong_inference` mappings across four different capabilities were all produced from the *same underlying source/event* rather than four independent corroborating pieces of evidence. This is also the root data gap behind the "acquisition" fan-out risk described below.

4. **Item 5 — Harden opportunity scoring against repeated-URL / same-event inflation.** `commercial/opportunities.py::_score` still uses **raw counts**: `len(unique_urls)` for a "corroboration" bonus, plus `direct_count` and `strong_count + signal_backed` bonuses — exactly the "raw mapping/source counts" the direction says to move away from. Without `inference_cluster_id`, the score has no way to discount multiple mappings that all trace back to one event/source, nor to reward genuine *domain* diversity (two URLs on the same domain currently count the same as two URLs on different domains) or *cluster* diversity. This is a second-order symptom of item 4 being unimplemented, not a separate bug.

5. **Item 6 — Deterministic `epistemic_status`** (`confirmed_evidence` / `inference_hypothesis`, app-assigned not AI-assigned). No such field exists on `CapabilityMapping`, `OpportunityHypothesis`, or anywhere in the AI layer. `evidence_level` is a reasonable *basis* for deriving it (e.g. `direct_evidence → confirmed_evidence`, `strong_inference`/`weak_relevance → inference_hypothesis`) but the explicit field the direction asks for does not exist, so nothing currently guarantees the AI narrative layer can't blur the two ("the evidence shows..." vs. "this is a hypothesis..." is currently left to prompt wording, not a structural field the UI can branch on).

6. **The concrete over-inference scenario itself is still reproducible.** Walking the catalogue: `"acquisition"` is a `generic_trigger` shared by **all five** capabilities (network, data centre, cloud/AI, cybersecurity, managed services). `"acquisition"` is not itself a recognized `signal_type` in `commercial/signals.py` — so on its own it only ever reaches `weak_relevance` (Rule 5). But if the *same source* also contains independent language matching any of the still-broad `_QUALIFYING_SIGNAL_TYPES` (e.g. "strategic partnership" or "investment") **anywhere in the text**, and "acquisition" itself sits in the same sentence as the organization's name, Rule 4 fires for **all five capabilities simultaneously** as `strong_inference` — reconstructing close to the exact fan-out pattern in the problem statement (five independent-looking opportunities from one loosely-related signal). This is the combined effect of gaps B.1, C.1, and C.2 above, not a fourth separate bug — fixing the localization (item 1 fully) and narrowing (item 2) together closes it.

## E. Tests that should be added

All new tests should follow the existing convention: generic placeholder organization names (e.g. `"Meridian Ports Authority"`), no real customer/sector/country references, in a new `tests/test_phase2_inference_hardening.py` (or split by concern):

1. `test_unrelated_signal_elsewhere_in_source_does_not_promote_generic_trigger` — the exact reported shape: a source with "acquisition" near the org name in one sentence, and "partnership"/"investment" in an unrelated sentence elsewhere → generic trigger must NOT reach `strong_inference` once signal-to-trigger locality is enforced (currently would fail — this is the regression test for gap B.1).
2. `test_partnership_investment_contract_award_never_independently_promote_generic_trigger` — direct test of item 2's narrowed set, for each of the three excluded signal types individually.
3. `test_genuine_local_expansion_event_still_produces_multiple_related_capability_hypotheses` — the "GOOD" example from the spec: one genuine, locally-associated "new facility" event legitimately producing several `strong_inference` mappings (network/data-centre/cybersecurity/managed-services) — proves the fix doesn't over-correct and destroy legitimate multi-capability inference (explicitly required: "do NOT optimize for fewer mappings").
4. `test_capability_mappings_from_same_event_share_inference_cluster_id` / `test_capability_mappings_from_different_events_have_different_cluster_ids`.
5. `test_evidence_category_assigned_per_classification_branch` — one case per branch (technographics, LinkedIn, direct/organizational event, procurement, generic+signal inference, incidental weak mention).
6. `test_epistemic_status_direct_evidence_is_confirmed_never_ai_assignable` / `test_epistemic_status_inference_levels_are_inference_hypothesis` — plus an AI-layer test proving a hallucinated `epistemic_status` in a fake AI payload is ignored/stripped (mirrors the existing `test_hallucinated_capability_id_is_dropped` pattern).
7. `test_opportunity_score_does_not_inflate_from_repeated_urls_on_same_domain` / `test_opportunity_score_rewards_genuine_domain_diversity_over_raw_count` / `test_opportunity_score_counts_inference_clusters_not_raw_mappings` — regression tests directly against item 5's stated failure mode.
8. `test_five_capabilities_from_one_weak_shared_generic_trigger_is_blocked` — an end-to-end pipeline test (source → signals → mapping) reproducing the "ONE unrelated partnership/acquisition fact should NOT automatically create five independent opportunities" example verbatim, asserting at most the legitimately-associated subset reaches `strong_inference`.
9. UI: `test_qualified_corpus_still_surfaces_disqualified_and_weak_evidence_counts` (once D's UI change lands) — a `ui/data.py`-level test rather than a Streamlit-rendering test, consistent with how `test_phase2_ui.py` tests helpers today rather than rendering.

## F. Proposed implementation order

Ordered so each step is independently testable and nothing downstream is built on a still-changing foundation:

1. **Data model first** — add `evidence_category`, `inference_cluster_id`, `epistemic_status` to `CapabilityMapping` (empty/derived defaults so nothing downstream breaks yet). Zero behavior change; existing 101 tests should stay green untouched.
2. **Signal-to-trigger localization + narrowed inference-qualifying signals** (B.1 + C.1 together, since they're two halves of the same fix and share test fixtures) in `evidence_mapping.py`. This is the core fan-out fix — do it before scoring changes so scoring is hardened against the *corrected* mapping output, not the old one.
3. **`evidence_category` assignment** per classification branch (mechanical, low-risk, now that the branches are finalized post-step 2).
4. **`inference_cluster_id` generation** (depends on step 2's grounding-signal logic being stable) + **`epistemic_status` derivation** (depends only on `evidence_level`, can be done in parallel with step 3).
5. **Thread the three new fields through `report.py`'s `chain_view()`/`to_dict()`** and the AI prompt block in `ai/prompt.py` (with the corresponding "AI must not invent these" instruction-text addition and a grounding test).
6. **Opportunity scoring hardening** (`opportunities.py`) — now that `inference_cluster_id` and domain data are available, replace raw-count bonuses with cluster/domain diversity.
7. **UI surfacing** — uncertainty visibility (corpus_reason/disqualified/weak counts always shown), the new fields in DECIDE/ACT, the pre-existing capability-summary display bug fix, and the WATCH/DECIDE product decision on opportunity-radar duplication (flag for your call, don't unilaterally redesign the tab).
8. **New tests throughout** (§E), added alongside each step rather than batched at the end, keeping the "baseline must be preserved, only removed if demonstrably obsolete" rule intact — none of the existing 101 tests should need to change; this whole plan is additive.
9. **Regression pass** — re-run the full suite (real pytest on your machine, given this sandbox's PyPI restriction) plus `before_after_demo.py`/`run_phase1c.py --mock` to confirm nothing in H1–H4/1D/1E/1F's accepted behavior moved.
