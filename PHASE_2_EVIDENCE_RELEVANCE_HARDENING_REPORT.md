# Evidence-Relevance Hardening — Implementation Report

Implements recommendations #1–#6 of `PHASE_2_EVIDENCE_RELEVANCE_AUDIT.md`. Recommendation #7
(direct_evidence tiering) was explicitly **not** implemented, per instruction. `ai/prompt.py`,
`ai/client.py`, and `ai/synthesis.py` (the AI reliability fixes from the prior pass) were **not**
touched. No live search was run; all work is static code/test changes plus one static test-corpus
JSON audit, both already completed before this implementation pass began.

## 2. Exact behavioral changes

**#1 — Evidence diversity scoring.** `commercial/opportunities.py::_score()` previously computed its domain/cluster diversity bonus over every `direct_evidence`/`strong_inference` mapping backing an opportunity. It now filters to only `organizational_technology_event` and `procurement_signal` category mappings before computing that bonus. Because every current `STRONG_INFERENCE` mapping is always categorized `business_signal_inference` (confirmed by re-reading both promotion paths in `evidence_mapping.py`), the practical effect is: an opportunity backed *only* by strong_inference evidence now scores as `best.confidence * 0.70` with **no** diversity bonus at all, however many domains/clusters back it; an opportunity with at least one direct_evidence/organizational-technology-event or procurement-signal mapping still earns bonus credit, but only from mappings of those two categories — a business_signal_inference mapping sitting alongside them contributes to the base evidence count shown to a viewer, but not to the score inflation. This is the direct fix for the audit's "5 independent domains, 4 of which don't corroborate" and "3 independent domains, 0 of which are clean IT-specific evidence" findings.

**#2 — Vendor case studies.** A new check, `_vendor_term_for_source_domain()`, matches a source's own domain (via per-label exact match after stripping non-alphanumerics, e.g. `zscaler.com` → label `zscaler`) against the same horizontal vendor lexicon already used for incumbent detection (`commercial.incumbents._KNOWN_VENDOR_TERMS` — no new vendor list introduced). When that vendor term is also independently detected as incumbent evidence in the *same* source's text, the source is treated as a vendor's own case study/marketing page about its own product, and folded into the same handling as third-party technographics (Rule 0): every capability match from that source is capped at `weak_relevance` / `current_state_technology`, never `direct_evidence` or `organizational_technology_event`. This is scoped to the **source's own domain** — a news article that merely *mentions* a known vendor by name (published elsewhere) is unaffected and can still promote normally (tested explicitly).

**#3 — Buzzword/list-like text.** `commercial/text_heuristics.py::looks_like_label_list()` flags a sentence-span as list-like when (a) it contains ≥5 capitalized/label-shaped tokens, (b) those tokens make up ≥70% of all words in the span (a density check — added specifically so an ordinary sentence that happens to mention a multi-word organization name, which contributes several capitalized tokens on its own, is not misflagged), and (c) no common action-verb-hint word is present. `looks_like_navigation_or_aggregator_text()` flags a span containing common page-chrome phrasing ("Read More", "Skip to content", "Related articles", etc.). Both feed `is_low_trust_span()`. `commercial/signals.py::extract_signals()` now skips any signal-pattern match that falls in a low-trust span, continuing to the next candidate match instead of accepting the first one unconditionally — a signal type with no non-low-trust occurrence in the source simply isn't extracted. `commercial/evidence_mapping.py`'s `_is_organization_associated()` and `_signal_locally_associated_with_trigger()` similarly exclude low-trust spans from both what counts as "the organization is mentioned here" and what counts as "the term/trigger occurs here" — so a capability keyword or a generic trigger whose only occurrence is inside a buzzword list can no longer be treated as organizationally associated, closing the exact gap that let the Rule 2/3 "two co-occurring specific terms" path promote a category-label list to direct_evidence.

**#4 — Aggregator/regional/government pages.** Two changes. First, `_org_core_tokens()` now accepts an optional `country` and excludes any token shared with the country name before the organization-association token-match runs — so "Verimark" (a country) no longer helps satisfy "this text is about Verimark National Airports Authority" the way a real org-specific token would; if excluding country tokens would leave zero tokens, the original (unfiltered) set is used instead, so this can only make the check *stricter*, never more permissive. `_required_org_token_hits()` also scales the required-token-match threshold with how many core tokens the name actually has (`max(2, ceil(n/2))`) rather than a flat "2 regardless of name length." Second, the low-trust-span exclusion from #3 directly covers "Read More"/navigation-concatenated text, so an aggregator/roundup page's chrome can't satisfy organization association even when it happens to contain both the org's name and a technology term. Third — and this is a previously undisclosed gap found while implementing #4, not part of any of the 7 numbered recommendations verbatim but squarely inside "strengthen organization association": Rule 2/3's `STRONG_INFERENCE` fallback branch (a signal-backed lone keyword match, below the direct_evidence bar) required **no organization association at all**. It now requires the same `org_associated` gate the direct_evidence branches above it already had. `country` is threaded as an optional parameter throughout (`map_source_to_capabilities`, `map_all_sources`, `_is_organization_associated`) and supplied by `research/analysis/report.py` from `run.organization.country` — always the dynamically resolved value, never hardcoded, and omitting it (as existing direct test callers do) reproduces the prior behavior exactly, so this is backward-compatible by construction.

**#5 — Customer-facing product pages.** `looks_like_customer_product_page(url, text)` requires *both* a product/pricing-shaped URL path (`/products?/`, `/pricing/`, `/plans?/`, `/cards?/`, `/loans?/`, `/accounts?/`, `/retail/`, etc.) *and* at least two distinct generic pricing/retail content markers ("apply now", "interest rate", "APR", "terms and conditions apply", "minimum balance", "starting at/from", etc.) — requiring both, rather than either alone, avoids over-triggering on (for example) a news article that merely mentions a product name once. When true, the source is excluded from Rule 4 (generic-trigger inference) and from Rule 2/3's `STRONG_INFERENCE` fallback branch — the two paths driven by generic business-signal wording, which is exactly what a product page's own marketing copy ("Business Expansion Loan", "capacity expansion for growing businesses") can spuriously trigger. Direct multi-keyword or tech-event-backed `DIRECT_EVIDENCE` promotion is deliberately left untouched, since a product page genuinely describing a concrete technology event backed by two or more specific capability terms is unlikely to be spurious wordplay, and over-suppressing there risks removing genuine evidence.

**#6 — Third-party executive biographies/interviews.** `executive_bio_marker_count(text)` counts distinct generic biographical/interview marker phrases ("is responsible for", "before joining", "in her role as", "holds a degree", "serves as the chief...", etc.) anywhere in a source's text. When a source has **two or more distinct** such markers (a deliberate threshold — see Known Limitations), it is folded into the same handling Rule 1 already gives a personal LinkedIn profile: every match from that source is capped at `weak_relevance`, and (except for LinkedIn job postings, which keep `hiring_intent_context`) the evidence_category becomes `stakeholder_context`. The final hard-clamp safety net at the end of `map_source_to_capabilities()` — previously scoped only to `is_linkedin_profile` — now also covers `is_executive_bio_source`, so this cap holds even if a future rule change reopens a bypass.

## 3. False-positive tests added (`tests/test_evidence_relevance_hardening.py` unless noted)

- `test_business_signal_inference_diversity_does_not_inflate_score` (in `tests/test_phase2_inference_hardening.py`) — #1: the original "reward domain diversity" fixture (generic-trigger/business_signal_inference) now scores identically regardless of domain count.
- `test_vendor_case_study_on_vendors_own_domain_is_not_promoted` — #2: a case study hosted on the vendor's own domain, naming that same vendor as an incumbent, is capped at weak_relevance/`current_state_technology`.
- `test_signal_pattern_inside_label_list_span_is_not_extracted_as_a_signal` — #3: a `technology_initiative`-triggering phrase inside a buzzword/label list is not extracted as a Signal.
- `test_buzzword_list_with_two_direct_terms_does_not_promote_direct_evidence` — #3: two distinct direct capability keywords inside a category-label list (even alongside the org's own name) do not satisfy the "≥2 co-occurring terms" direct_evidence path.
- `test_country_level_reference_does_not_satisfy_organization_association` — #4: a government/ministry page mentioning the country name plus one generic word no longer satisfies organization association for an org whose name contains that country.
- `test_read_more_navigation_concatenation_is_treated_as_lower_trust` — #4: "Read More"-chrome text containing both the org name and a generic trigger does not promote.
- `test_rule_2_3_strong_inference_fallback_now_requires_organization_association` — #4: a signal-backed lone keyword match nowhere near the target organization no longer promotes via the previously-unguarded fallback branch.
- `test_retail_product_page_expansion_wording_does_not_promote_internal_signal` — #5: a retail loan/product page's "Business Expansion Loan" / "capacity expansion" marketing copy does not promote an internal organizational signal.
- `test_generic_executive_bio_content_is_treated_as_stakeholder_context` — #6: a third-party CIO-bio/interview article with a vague "responsible for digital transformation" line is capped at weak_relevance/`stakeholder_context` across every capability it would otherwise have fanned out to.
- `test_same_vendor_mentioned_on_non_vendor_domain_is_unaffected_by_case_study_rule` — #2 control: confirms the rule is domain-scoped (a supporting/negative-control test, not itself a reproduction of a false positive).

## 6. Known limitations

- **Recommendation #2 applies per-source, not per-capability "competes with this vendor."** The audit's wording ("a capability that competes with that vendor's own offering") implies a vendor→capability competition mapping; building one deterministically would itself require additional hardcoded domain knowledge (which vendor competes with which Otech capability), so instead every capability matched in a confirmed vendor-case-study source is capped uniformly. In the audit's own findings this produces the correct outcome (both Zscaler-case-study rows were flagged), but a source where a vendor case study genuinely also contains an unrelated, organization-specific technology event for a *non-competing* capability would be over-suppressed by this pass.
- **Recommendation #4's Rule 2/3 org-association fix is a genuine gap-close, not a verbatim item from the numbered list.** It's implemented because it's squarely inside "strengthen organization association," but it was discovered during implementation rather than named explicitly in the audit's 7 recommendations. Flagging this so it's not mistaken for scope creep beyond #1–#6.
- **The executive-bio marker threshold (≥2 distinct markers) is a deliberate, disclosed trade-off.** It avoids over-triggering on a genuine announcement that happens to include one biographical clause, but a third-party profile article with exactly one strong marker phrase plus otherwise-vague "digital transformation"-style language will not be caught by this rule (it would still need to independently fail Rule 2/3/4's other bars to avoid promotion).
- **The country-exclusion in recommendation #4 only takes effect when `country` is supplied.** The real pipeline (`research/analysis/report.py`) always supplies it now; any other/future direct caller of `map_source_to_capabilities`/`map_all_sources` that omits `country` will not get this protection (by design, for backward compatibility) — this is disclosed in the function's own docstring.
- **Not addressed, per the audit's own "secondary observation" framing (recommendation #7) and this task's explicit instruction:** the direct_evidence/strong_inference tiering question (e.g., SC's Microsoft press release and Siemens' NVIDIA statements reading like explicit organizational statements but classifying as strong_inference) is untouched.
- **Two false-positive mechanisms noted during analysis but out of scope for #1–#6, disclosed rather than silently left unaddressed:** (a) generic-verb overreach — a signal pattern like "upgrading skills" (employee training) can still satisfy the `technology_initiative` signal pattern's `upgrad(e|es|ed|ing)` alternative outside of a low-trust span, which is a pattern-breadth issue in `commercial/signals.py` unrelated to any of #1–#6; (b) capability-specific semantic disambiguation — "capacity expansion" describing *manufacturing/renewable-energy* capacity (a real audit finding: Siemens Gamesa wind-turbine earnings commentary) is structurally indistinguishable, at the deterministic-regex level, from *IT* capacity expansion for the Data Centre & Infrastructure capability; nothing in #1–#6 targets this, since doing so deterministically without sector-specific hardcoding is a materially harder problem than the six recommendations actually implemented.
- **Heuristic, not NLP.** As with every prior phase, the sentence-span, label-list, navigation, product-page, and executive-bio detectors are disclosed regex/lexical heuristics, not real natural-language understanding — they will miss some real instances of each pattern and could, in an adversarially-worded source, still be evaded. They are deliberately conservative (biased toward not creating new false negatives on genuine evidence) rather than exhaustive.
